Migration safety:
The migration checks for utf8mb4_nopad_bin before changes, preserves indexes, and leaves
SQLite unchanged. Unsupported engines fail explicitly rather than silently using PAD SPACE.
Downgrading to case-insensitive/PAD semantics can collapse newly valid identities; down()
therefore refuses on MariaDB/MySQL. Use a separately reviewed forward migration.
MariaDB DDL is not fully transactional: back up V2 and validate/recover partial DDL explicitly
if an ALTER fails. Production migration is not performed here.
Drain old workers before deploying generation fencing; old application binaries do not
recognize the new ownership counters.

Official collation reference:
https://mariadb.com/docs/server/reference/data-types/string-data-types/character-sets/supported-character-sets-and-collations

TRANSACTIONS / LOCK ORDER

Native invoice creation:
Transaction -> company FOR UPDATE -> idempotency/payload-hash check -> MAX(sequence)+1 ->
invoice and lines. Company+number, company+sequence and company+creation-key uniqueness.
Rollback removes allocation; no standalone counter is consumed. Distinct companies use
different row locks. Existing draft deletion/numbering contract is unchanged.

FBR draft creation:
Transaction -> company FOR UPDATE -> creation-key/hash -> nonhistorical MAX(sequence) ->
skip any historical number collision -> dedicated invoice/lines/audit.
Independent tables, no accounting posting. Number/key/source unique constraints retained.

Both submission lifecycles (independent):
Preparation transaction -> invoice FOR UPDATE -> company-scoped attempt FOR UPDATE ->
configuration/payload/key/lease checks -> bounded claim_generation increment.
Provider call is outside the transaction. Completion/failure -> invoice -> attempt locks ->
generation and pending-state checks before any mutation. Lease stays two minutes; provider
idempotency keys retain accounting: and pkfbr: namespaces. Retries keep the original key.
Generation exhaustion fails closed before provider invocation.
Provider acceptance itself cannot be rolled back. Fencing protects local state, not external
exactly-once delivery; real provider idempotency and reconciliation require staging evidence.

Historical import:
Start/resume transaction -> company -> run FOR UPDATE -> bounded execution_generation increment.
Every mapping, pre-chunk exception ledger write, chunk (records/maps/evidence/progress),
completion/reconciliation and failure transition rechecks ownership under company -> run.
Explicit resume supersedes the old generation. Completed replay is read-only and does not
increment. Already committed chunks survive a stale worker failure.
Run identity remains system+fingerprint+company; source-company mapping retains global source
and target uniqueness. Conflicting mappings return validation conflicts.
Historical imports never resolve/call an FBR provider or native posting service.

Deadlock policy:
Existing service transactions use one attempt unless explicitly configured otherwise.
No retry loops were added. Audit found consistent company->run and invoice->attempt order
in changed paths. Submission configuration reads do not lock company, avoiding a reverse
company/invoice lock chain. Cross-company unique-index contention can still deadlock.
The manual probe intentionally locks two company rows in opposite order, requires one
explicit MariaDB 1213 victim, checks a single attempt and no partial commit. It is an engine
rollback/visibility probe, not proof that every possible application deadlock is absent.
