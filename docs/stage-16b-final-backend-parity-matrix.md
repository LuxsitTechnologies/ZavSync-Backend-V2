## Open policy boundaries and non-portable V1 behavior

1. V1 `ProfileController` returns a raw User/Employee relation and lets the Employee edit address/DOB/gender; V2 must define ownership and an allowlisted resource first.
2. V1 `AnnouncementController` stores attachments on the public disk and selects recipients by role title. Neither pattern is portable. Company-wide publication through V2 RBAC/notifications is the conservative subset.
3. V1 `SwapRequestController` accepts `requested_by_employee_id` from a request and swaps assignment rows without a single fenced transaction. V2 must derive the requester and lock/version both sides.
4. V1 document folders and `assigned_to_user_id` do not by themselves establish employee disclosure authority. Generic V2 `DocumentService` ownership is not the same as employee visibility.
5. V1 expense/disbursement and inventory issuance have different authority models from V2 Accounting/Banking/Inventory. Claim/approval and request/approval must not be conflated with payment, posting or stock fulfilment.
6. Prototype 2FA, bank/tax display, fake late/overtime totals, task progress, status badges, birthday/meeting events, and unified withdrawal actions are not authoritative backend requirements.

This matrix must be updated whenever an audited decision or implemented slice changes a row's disposition. No V1 production database or files were accessed for this inventory.
