# Stage 16B-FINAL employee portal backend contract

Status: frozen backend handoff for the separate frontend workspace. Base path is `/api/v1`; all routes below require Sanctum authentication, an active company context and company-scoped RBAC. The new operational domains use the existing **payroll** commercial entitlement; `GET employee/me` remains the existing identity read and reports editability without requiring that entitlement. A platform administrator is not exempt from company permissions. IDs in paths are UUIDs unless the existing API says otherwise. The frontend must not infer permission from a visible navigation item: use navigation visibility for presentation and let the API enforce authorization.

This document covers the new Stage 16B-FINAL endpoints. Existing certified Payroll, Attendance, Leave, Tasks, Tickets, Notifications, and account APIs retain their earlier contracts; do not replace their adapters or invent a new aggregate write endpoint. The employee profile endpoint is extended here. Every paginated response has `{data: T[], meta: {total, current_page, last_page}}`; `per_page` is normally 1–50 (default 20) where accepted. Detail/action responses are unwrapped JSON objects. Validation errors use the existing V2 error envelope; structured domain conflicts carry the error codes below. Do not display raw storage paths, secrets, internal hashes or raw Employee/User models.

## Identity, navigation, and entitlements

Employee self-service resolves `User → active CompanyUser → same-company Employee`. A missing link is not repaired by matching names or emails. Employee reads and writes use the named permission in the route tables below; company switch changes the entire query scope. All new navigation identities use the existing `payroll` entitlement, not a new commercial module:

| Identity | Required permission |
|---|---|
| `employee.profile`, `employee.documents`, `employee.announcements`, `employee.directory`, `employee.teams` | `employee.self.view`, `employee.documents.view`, `employee.announcements.view`, `employee.directory.view`, `employee.teams.view` respectively |
| `employee.assets`, `employee.expenses`, `employee.schedule`, `employee.shift_swaps` | `employee.assets.view`, `employee.expenses.view`, `employee.schedule.view`, `employee.schedule.view` respectively |
| `hrm.employee_documents`, `hrm.announcements`, `hrm.teams`, `hrm.asset_requests` | `employee.documents.admin.view`, `announcements.view`, `teams.view`, `assets.view` respectively |
| `hrm.expenses`, `hrm.expense_categories`, `hrm.shifts`, `hrm.rotas`, `hrm.shift_swaps` | `expenses.view`, `expenses.categories.manage`, `schedules.view`, `schedules.view`, `schedules.view` respectively |

Other existing employee/admin navigation items retain their pre-Stage-16B-FINAL identities. The frontend may compose dashboard, calendar and Requests screens from authorized domain reads, but may not fabricate counts, statuses, meetings, birthdays, payments or stock fulfilment.

Methods and paths below are exact; prefix each with `/api/v1/`. `:id` in this document denotes the named UUID path parameter. Permissions are per operation, not a grant to every route in the group.

Binary download/attachment/receipt routes return a private streamed response, not a JSON file URL.

## Requests and response shapes

Required `Idempotency-Key` headers are opaque exact values of 8–200 characters; generate a fresh key per new intent, persist it across transport retries, and never reuse it for changed content. A replay with the same key/payload returns the existing object; a changed payload is a conflict. Do not send an idempotency key instead of the `version` required by stale-write actions.

| Resource | Write request | Response fields / constraints |
|---|---|---|
| Self profile | `PATCH employee/me`: `{address: string|null, version: integer}`; only those two fields accepted | `GET` and successful `PATCH` return `{linked, employee, self_editable}`. Employee resource: `id, employee_code, full_name, email, phone, department, designation, employment_type, status, joining_date, leaving_date, location, address, self_profile_version`. Address is the only self-editable Employee field. |
| Emergency contact | `POST`: `{name, relationship, phone}` + key; `PATCH`: same fields + `version`; `DELETE`: `{version}` | `{id, name, relationship, phone, version, created_at}`; delete returns `{status:"REMOVED"}`. Third-party contact PII is self-only. |
| Personal document | Multipart `POST employee/documents`: `file` + key | `{id, category:"PERSONAL"|"ISSUED", original_filename, mime_type, size_bytes, checksum_sha256, created_at}`. Employee list includes own uploads and only released issued files. |
| HR-issued document | Multipart `POST hrm/employee-documents`: `employee_id`, `file` + key; `POST .../release`: no body | Admin card additionally includes `employee_id, released_at, released_by`; issued file is invisible to employee until release. Release is idempotent. No retraction endpoint. |
| Announcement | `POST`: `{title, description, priority:"LOW"|"NORMAL"|"HIGH", expires_at?: date|null}` + key; `PATCH`: same plus `version`; `POST .../attachment`: multipart `file`, `version` + key; `POST .../publish`: `{version}` | `{id, title, description, priority, status, version, published_at, expires_at, attachment:{id,original_filename,mime_type,size_bytes}|null, created_at}`. The same release principle already applies separately to payroll payslips: POSTED alone does not mean employee-visible.

## State and concurrency rules

| Domain | Authoritative transition | Not permitted / frontend presentation |
|---|---|---|
| Documents | Personal upload is immediately owner-readable. HR-issued upload → unreleased → explicit admin release → employee-readable. | Upload/assignment is not publication; no delete/retraction/verification workflow. |
| Announcements | `DRAFT` → `PUBLISHED`; expiration hides from employee feed without rewriting publication history. | Drafts and expired items do not appear in employee reads; no role-title targeting or read receipt. |
| Teams | Membership and manager links are explicit; lead must be an active member; manager cycle is forbidden. | Department is not manager/team; former employees are excluded from current directory/team changes. |
| Rotas | Day shift (`end_time > start_time`) → draft rota/slots/assignments → published rota → self schedule. `required_coverage` is a minimum target. | No overnight/DST-crossing shift, no employee time overlap, no attendance or payroll rewrite. |
| Swaps | Request → `PENDING_TARGET` → target acceptance → admin approval or rejection; target decline is terminal. Approval exchanges the two assignment employees under locks/version checks. | Target consent cannot be skipped; requester cannot approve own swap; stale assignments require refresh. |
| Equipment | `NEW_EQUIPMENT` request `PENDING` → admin `APPROVED` or `REJECTED`. | `APPROVED` does not mean fulfilled, issued, returned or deducted from stock. |
| Expenses | `DRAFT` → `SUBMITTED` → `APPROVED` or `REJECTED`. Draft may be edited and receive one private receipt before submission. | `APPROVED` does not mean paid/reimbursed/posted. Admin may not approve own claim. |

Creation/retry actions use exact-key idempotency. Versioned writes compare the submitted `version` with the authoritative current version under a transaction/lock, increment on a real mutation and fail closed on stale or exhausted version. On 409, reload the detail, show the updated state, and ask the user to retry the new intent; do not silently resubmit a stale decision. All current-company scope and parent ownership checks apply to file and nested resources. Structured conflicts include `*_KEY_REQUIRED`, `*_IDEMPOTENCY_CONFLICT`, `*_VERSION_STALE`, `*_VERSION_EXHAUSTED`; specific guards include `EMPLOYEE_PROFILE_FIELD_FORBIDDEN`, `EMPLOYEE_IDENTITY_NOT_LINKED`, `EMPLOYEE_*_INACTIVE`, `ANNOUNCEMENT_ALREADY_PUBLISHED`, `ANNOUNCEMENT_EXPIRY_INVALID`, `TEAM_LEAD_MEMBERSHIP_REQUIRED`, `MANAGER_CYCLE_FORBIDDEN`, `SCHEDULE_ASSIGNMENT_CONFLICT`, `SCHEDULE_DATE_PAST`, `SWAP_ASSIGNMENT_STALE`, `SWAP_NOT_READY_FOR_DECISION`, `ASSET_REQUEST_SELF_DECISION_FORBIDDEN`, `EXPENSE_CLAIM_NOT_EDITABLE`, `EXPENSE_CLAIM_NOT_SUBMITTABLE`, `EXPENSE_CLAIM_SELF_APPROVAL_FORBIDDEN`, and `FILE_NOT_FOUND`. Validation errors are 422, stale/conflict errors 409, forbidden access 403 and invisible/non-owned resources 404; use the response's actual `error_code` and message, not string matching.

For manager administration specifically, `GET /api/v1/hrm/employees/{employee}/manager` is an authenticated, active-company, payroll-entitled read requiring `teams.view`. It returns only `{employee_id: UUID, manager_employee_id: UUID|null, version: positive integer}`; `null` manager still has a version. The GET does not write, notify or increment that version. Use its `version` in the existing `PATCH /api/v1/hrm/employees/{employee}/manager`, which still requires `teams.manage`. A concurrent manager change increments the relationship version; a subsequent PATCH with the old version returns 409 `TEAM_VERSION_STALE` when proposing a different manager. A foreign-company or missing employee is 404; missing permission or payroll entitlement is 403 (`MODULE_NOT_ENTITLED` for the latter). Platform-admin status alone does not bypass these checks. Refresh GET after a stale response; do not guess or make `version` optional.

## Former employees, notifications, company time, and firewalls

An active membership and explicit link/permission may continue to read historical, authorized payroll/attendance/leave/work/private-document/expense/asset records as each existing domain permits. Resigned/terminated employees cannot create or mutate the new self profile, documents, contacts, equipment requests, expense claims, or shift swaps; the current colleague directory/team are not former-employee disclosure surfaces. `GET employee/schedule` may return published historical assignments but caps a former employee's requested range at the day before the current company-local date. Do not implement a frontend status override to bypass backend 403/409/404 decisions.

Announcement publication, claim submission/decision, asset decisions and swap decisions use existing V2 audit and preference-aware notification infrastructure where the service emits them. Notifications are in-app and transaction-aware; the frontend must not claim email delivery or invent a second inbox. Publication/release is explicit: HR document release and payroll payslip release are distinct actions. Employee announcement visibility uses publish/expiry, and employee schedule visibility uses rota publication.

Rota dates and shift times are company-local calendar values, with the company timezone captured in the rota and returned on schedule cards. Do not convert an `HH:mm` shift to a different calendar date in the browser. Dates on expense claims and other date-only fields remain `YYYY-MM-DD`; timestamps are ISO-8601. Commercial/permission checks and data queries always use the currently selected company; discard cached portal data on company switch.

Stage 16B-FINAL writes must not create or modify Payroll, Attendance, Leave, Native Accounting invoices, journals, AR, customer payments, Banking, Inventory movements or CRM records. Expense approval and equipment approval are operational decisions only. The existing Payroll, Attendance, Leave and Work domains keep their separately certified lifecycles. Historical V1 portal data was not imported or accessed.

## Deliberate deferrals and frontend honesty

No authoritative contract exists here for employee asset custody/issuance/return/damage or Inventory fulfilment; expense reimbursement/Banking settlement or GL posting; overnight shifts; leave/attendance/payroll effects of a rota; document verification/expiry/required status; announcement role-targeting/read receipts; salary revision chart/PDF; fabricated late/overtime/absence classifications; prototype 2FA/backup codes; education/experience self-edit; bank/tax self-disclosure; task progress/project; birthday/meeting/calendar inventions; generic cross-domain withdrawal; or remaining V1 historical portal migration. Display an honest unavailable state for those controls, not a mock, fake total, optimistic mutation, or alternate local-only lifecycle. The parity matrix records the exact disposition and reason for each capability.
