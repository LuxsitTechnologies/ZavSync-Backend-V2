All paths below are relative to `/api/v1`. Unless marked public or pre-approval, they require Sanctum, `X-Company-Id` for an active membership in an **approved, active** company, and the stated company permission. Cross-company/private resource IDs must not be treated as globally discoverable. Except where stated, reads have no version or idempotency input, and non-list responses are not paginated. Use the structured `error_code` when supplied; generic validation returns field-level `422` errors.

## 22: Admin Company Profile

POST `/api/v1/platform/companies` requires an authenticated **email-verified** identity, plan ID, company name/currency/timezone/country and accepts optional company size/province/email/phone/address/tax identifier plus exact ASCII `Idempotency-Key` (1–100 chars, `[A-Za-z0-9._:-]+`). It also accepts optional write-only `fbr_token` with required `fbr_environment` SANDBOX/PRODUCTION; supplying a token requires numeric 7/13-digit tax ID, active PROVINCE code and seller address. Same actor/key/payload replays the existing company; changed payload conflicts. It creates one pending Company, membership, settings and `PENDING_APPROVAL` subscription with null trial start/end. A public visitor must register and verify email first; anonymous company creation is unavailable.

GET `/api/v1/platform/company-profile` requires selected approved company and `platform.settings.view`; PATCH requires `platform.settings.manage`, `profile_version`, and any of name/company_size/province_code/email/phone/address/tax_identifier. Before approval, the verified founder may instead GET/PATCH `/api/v1/platform/companies/{company}/pending-profile` while an active member with `platform.settings.view/manage`; this is unavailable after approval. A stale version returns `409 COMPANY_PROFILE_VERSION_STALE`. Changing `tax_identifier` additionally requires `platform.settings.high-risk`. An approved profile cannot be edited into a legally incomplete state (`409 COMPANY_PROFILE_INCOMPLETE`); the existing `/platform/settings` route also refuses clearing approved legal email/tax identity. Response includes approval/activity separately and `fbr_credential_configured` only, never a secret.

GET `/api/v1/platform/admin/companies` requires an actual platform administrator with `platform.companies.view` in the selected approved administration company; supports bounded search/page/per_page and approval/activity filters. GET `/platform/admin/companies/{company}` has the same authority. PATCH `/platform/admin/companies/{company}` additionally requires active **target-company** membership and `platform.settings.manage` there, with `profile_version`; high-risk tax changes additionally require target `platform.settings.high-risk`. POST `/platform/admin/companies/{company}/approval` requires `platform.companies.approve`, `approval_status` APPROVED/REJECTED and `profile_version`. Approval requires company contact email, 7–13 alphanumeric tax ID and active PROVINCE reference; otherwise `409 COMPANY_PROFILE_INCOMPLETE`. First approval changes the pending subscription to `TRIALING` and starts its 14-day clock; repeat/re-approval never restarts it. Approval/rejection produces a founder notification. PATCH `/platform/admin/companies/{company}/activity` requires `platform.companies.activate`, `is_active` and `profile_version`; it refuses deactivating the selected administration context. Transitions return the minimized profile and preserve approval/activity as separate values. No hard-delete exists; deactivation retains history. FBR credential replacement uses the separate encrypted configuration contract. Legal contact email is not the identity/login email; unlike V1's shared create flow, V2 does not impose a cross-table uniqueness rule between these distinct authorities.

Internal calendar events: GET/POST `/api/v1/ai/intelligence/calendar/internal-events`, GET/PATCH `/api/v1/ai/intelligence/calendar/internal-events/{event}`, and POST `/api/v1/ai/intelligence/calendar/internal-events/{event}/cancel` require an approved active selected company, `ai` entitlement and `intelligence.calendar.manage`. GET list supports `from`/`to` ISO instants with explicit offsets, `page`, `per_page` (1–100), returning a paginator. POST accepts `title` (1–255), optional `description` (max 10000), and `starts_at`/`ends_at` ISO dates with explicit UTC offset; end must be after start. PATCH accepts `version` and any editable fields; cancel accepts `version`. Responses contain only `id`, `title`, `description`, UTC `starts_at`/`ends_at`, snapshotted company `timezone`, `status` ACTIVE/CANCELLED, `version`, and `cancelled_at`. The organizer alone can read or mutate an event, even when another user has the same permission. Cross-tenant/cross-organizer IDs return 404. Stale version and cancelled edit return 409 with `CALENDAR_EVENT_VERSION_STALE`/`CALENDAR_EVENT_CANCELLED`; repeated cancel is idempotent. This does not create a provider calendar event or send invitations.

Dashboard layout GET accepts `accounting.view`, `platform.settings.view`, or `platform.settings.manage`; PUT/DELETE require `platform.settings.manage`. PUT body is `{layout_version, columns:1..4, widgets:[{key,visible}]}` with each of `revenue`, `outstanding`, `collected`, `overdue`, `invoiced_collected`, `pending_attention`, `recent_invoices` exactly once in desired order. DELETE body is `{layout_version}` and resets to defaults. Response includes catalog permission/entitlement availability, ordered widgets with `effective_visible`, columns, and version. Stale writes return `409 DASHBOARD_LAYOUT_VERSION_STALE`. The frontend must still independently authorize every underlying data request.

## Error and safety rule

Handle `401` unauthenticated, `403` permission/entitlement, `404` cross-company or deleted resource, `422` field validation/lifecycle, `409` idempotency/conflict and `503 FBR_UNAVAILABLE` without substituting mock success. Do not treat a redirect, timeout or pending status as provider success. No FBR Invoice endpoint creates a native Accounting invoice, journal, AR, payment, inventory movement or banking effect.
