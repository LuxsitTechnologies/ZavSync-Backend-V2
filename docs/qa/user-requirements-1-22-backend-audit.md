## Architectural constraints and decisions

- **Native Accounting** remains `/api/v1/accounting/*`, `Invoice`/`InvoiceLine`, `InvoiceService`, `InvoicePostingService`, AR/payments and journal authority. **FBR Invoice** remains `/api/v1/pakistan-fbr/*`, `PakistanFbrInvoice`/`PakistanFbrInvoiceLine`, separate attempts and no automatic Accounting effects. V1's shared-row accounting calls are evidence of historical behavior, not an instruction to reconnect domains.
- A submitted FBR document stores buyer snapshot and lines. This work captures seller fields and company email/phone at the first provider claim, preserves them for same-key retries, and refreshes them only for a new claim after an explicit provider rejection. Later configuration edits do not rewrite an accepted document. Full branding/document/QR print parity remains unverified.
- Deployed V1's `FbrInvoicesController` uses float arithmetic and an inconsistent header total (subtotal + sales tax versus line total also including extra/further tax). Approved V2 dedicated-domain integer calculation uses taxable + authoritative sales + extra + further; withholding is separate. Historical imported values must not be recalculated.
- Deployed V1 direct retries lack lease/fencing; V2 dedicated attempts use claim generation and server-authoritative retry. Do not copy V1 retry code or call live FBR.
- V1 source observations do not certify actual FBR provider acceptance, QR algorithm, billing provider, or deployed Portal Settings UI. Those remain explicitly unverified.
